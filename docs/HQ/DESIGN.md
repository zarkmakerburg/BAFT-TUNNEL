# طراحی مرکز فرماندهی BAFT-TUNNEL

**وضعیت:** تأییدشده توسط مالک — 2026-11-11  
**مخزن:** `zarkmakerburg/BAFT-TUNNEL`  
**شاخه طراحی/اجرا:** `docs/hq-command-center-foundation`

## هدف
ایجاد یک مدل فرماندهی سبک، repository-native و قابل‌گسترش برای چند پروژه؛ شروع با BAFT-TUNNEL. HQ نقطه ورود مشترک چت‌ها و عامل‌های توسعه است و وضعیت واقعی را از GitHub، محیط توسعه، CI و LAB می‌گیرد.

## معماری پذیرفته‌شده
- **GitHub مرجع حقیقت کد و چرخه تغییرات** (branch، commit، PR، CI و Issue).
- **Issue #2 مرجع واحد عملیات، تصمیم‌ها، شواهد، ریسک‌ها و handoffهای BAFT-TUNNEL**؛ تاریخچه آن append-only باقی می‌ماند.
- **مخزن محل نگهداری قراردادهای مشترک**: `AGENTS.md` و `docs/HQ/`.
- **ابزارهای متصل، مجریان عملیات‌اند**؛ HQ هماهنگ‌کننده است و نباید ادعای اجرای کاری را بدون خروجی ابزار مطرح کند.
- Workerها در شاخه/worktree ایزوله کار می‌کنند؛ یک مالک QA/ادغام‌کننده مسئول پذیرش شواهد و جمع‌بندی است.
- هر پروژه آینده باید فضای مستقل، شناسه پروژه و برد/شواهد مستقل داشته باشد؛ داده‌ها و دسترسی‌ها بین پروژه‌ها مخلوط نشوند.

## محدوده نسخه اول
1. نقطه ورود سراسری مخزن در `AGENTS.md`.
2. راهنمای HQ و مدل نقش‌ها، چرخه کار و گیت‌های تحویل.
3. فهرست ابزارها و ماتریس انتخاب Skill بر اساس نوع وظیفه.
4. فرمان‌های متنی استاندارد برای ادامه، بررسی وضعیت، برنامه‌ریزی، اجرا و گزارش.
5. قالب‌های Task، Handoff و Evidence.
6. برنامه پیاده‌سازی و چک‌لیست اعتبارسنجی اسناد.

## قرارداد عملیاتی
- ابتدا وضعیت زنده مخزن، شاخه، PRهای مرتبط و checkout را بررسی کن؛ هیچ تغییر فعالی را بازنویسی نکن.
- قبل از تغییر، مالکیت فایل/شاخه و تمیز بودن workspace را احراز کن.
- از Skill تخصصی متناسب با کار استفاده کن؛ بارگذاری بی‌هدف همه Skillها ممنوع.
- از ابزار موجود مناسب استفاده کن؛ برای عملیات محلی، ترمینال مجاز؛ برای GitHub، connector/API؛ برای CodSpeed، benchmark واقعی.
- هر ادعای PASS باید به SHA و شناسه تست/CI/LAB قابل پیگیری متصل باشد. UNKNOWN به PASS تبدیل نشود.
- simulation، تست محلی، CI میزبانی‌شده و LAB واقعی دو‌میزبانه جدا گزارش شوند.
- Secret، token، کلید خصوصی، مقدار محرمانه و آدرس حساس میزبان در مستند عمومی یا log ثبت نشود؛ فقط نام متغیر Secret در صورت نیاز.
- شاخه‌های موجود، PRها، stashها و checkoutها حفظ شوند؛ reset مخرب، force-push و حذف شاخه بدون ضرورت و مجوز ممنوع.
- Merge، Release و Deploy گیت‌های جداگانه‌اند؛ این بنیاد HQ مجوز عبور از هیچ‌کدام را صادر نمی‌کند.
- تغییرات production و hostهای پایدار خارج از محدوده این کارند.
- Issue #2 به‌روزرسانی عملیاتی را نگه می‌دارد؛ اسناد طراحی/راهنما جایگزین تاریخچه عملیاتی آن نمی‌شوند.

## ابزارها و Skillها
- GitHub: وضعیت repository، Issues، PR، branch، commit، workflow و review.
- Remote Desktop Commander: دسترسی مجاز به Mac/terminal و checkoutهای موجود.
- CodSpeed: benchmark و مقایسه کارایی؛ نتایج فقط پس از اجرای واقعی و مشاهده CI معتبرند.
- Context7: مستندات جاری کتابخانه‌ها و APIها هنگام نیاز.
- Superpowers: brainstorming، plan، TDD، debugging، verification و worktree بر اساس نوع کار.
- Figma: طراحی/بازبینی UI؛ فقط وقتی task طراحی رابط است.
- Linear/Notion و ابزارهای deploy/observability: اختیاری و فقط در صورت نیاز واقعی task؛ منبع وضعیت موازی نسازند.
- اتصال یا نصب Plugin نیازمند اقدام صریح کاربر است؛ ابزارهای حاضر دوباره نصب/پیشنهاد نمی‌شوند.

## خارج از محدوده
- داشبورد وب مستقل، سرور مرکزی، دیتابیس جدید، سیستم صف یا Agent runtime جدید.
- تغییر visibility مخزن، secrets، branch protection یا دسترسی‌ها.
- ادغام PRهای فعال یا شروع Release/Deploy.
- جابه‌جایی/بازنویسی کارهای CodSpeed یا LAB فعال.

## معیار پذیرش
- یک نقطه ورود روشن در root وجود داشته باشد.
- نقش‌ها، چرخه task، معیار شواهد، مرز دسترسی و گیت‌های انتشار بدون تناقض مستند باشند.
- ماتریس ابزار/Skill برای taskهای متداول، انتخاب ابزار درست و حداقل‌گرایی را مشخص کند.
- قالب‌ها قابل کپی و فاقد داده محرمانه باشند.
- لینک‌های داخلی معتبر، فایل‌ها از نظر Markdown خوانا و diff پاک باشد.
- هیچ PR، branch یا اجرای فعال موجود آسیب نبیند.
